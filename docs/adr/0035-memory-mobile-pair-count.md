# ADR-0035: 神経衰弱のペア数を可変にし、モバイル縦のデフォルトを下げる

## Status

Accepted

## Date

2026-07-28

## Context

神経衰弱（Memory）の「モバイル縦画面で盤面が収まらない」問題は **5 回起票されている**（[#965](https://github.com/yuta-yoshinaga/go_trumpcards/issues/965) → [#993](https://github.com/yuta-yoshinaga/go_trumpcards/issues/993) → [#1058](https://github.com/yuta-yoshinaga/go_trumpcards/issues/1058) → [#1367](https://github.com/yuta-yoshinaga/go_trumpcards/issues/1367)）。毎回「部分的に改善 → まだ収まらない → 再起票」を繰り返してきた。

再発の原因は実装の質ではなく、**ゴール自体が達成不可能だったことが一度も明文化されなかった**ことにある。

### 収容できないことの算数（375×667, 2026-07-28 実測）

| 制約 | 値 | 出典 |
|------|-----|------|
| タップターゲット最小 | 44×44 px | [DESIGN.md](../../DESIGN.md) "Interactive Element Minimum Size"（WCAG 2.5.5 AAA）。`bun run check` の tap-targets ガードで機械的に強制 |
| 盤面に使える幅 | 335 px | プレイエリア 375 − `px-4` 32 − ボード `p-1` 8 |
| 盤面に使える高さ | 286 px | プレイエリア 392 −（スコア行 28 + 獲得ペア 32 + メッセージ 46） |

```
最大列数: 7   （7×44 + 6×2 = 320 ≤ 335、8列は 8×44 + 7×2 = 366 > 335）
行ピッチ: 46  （44 + gap 2）
最大行数: 6   （286 / 46 = 6.2）
∴ 収容可能 = 7 × 6 = 42 枚 = 21 ペア
```

**52 枚（26 ペア）は 44×44 を守る限り物理的に入らない。** これが 5 回再発した理由である。

なお [#4445](https://github.com/yuta-yoshinaga/go_trumpcards/pull/4445) 以降、document 自体はスクロールしない（あふれはプレイエリア内で吸収される）。したがって旧 issue の「約 2000px の縦スクロール」という記述はもはや現象として存在せず、残っている問題は **「盤面を一望できない」** の一点に絞られる。

### 検討した代替案

1. **クロームを 88px 削る**（スコア行・獲得ペア・メッセージボックスをプレイエリアから除去）— いずれも実際に使われている情報。フッターへ移しても `shrink-0` なのでプレイエリアが同量削られ、差し引きゼロ。将来クロームが 1 行増えるだけで再発する。
2. **このグリッドだけタップターゲットを緩める**（38×38 なら 320px で収まる）— DESIGN.md 違反、かつ tap-targets ガードに例外を開ける必要がある。後日のアクセシビリティ監査で差し戻される公算が高く、振り子を止められない。
3. **42/52 で妥協する** — ゴールを据え置いたままなので確実に再起票される。
4. **ペア数を可変にし、モバイル縦のデフォルトを下げる** — 「52 枚を収める」という達成不可能なゴールを、達成可能なゴールに置き換える。[#1058](https://github.com/yuta-yoshinaga/go_trumpcards/issues/1058) が既に提案していたが未実装だった案。

## Decision

**案 4 を採用する。**

- `MemoryConfig` に `PairCount` を追加し、盤面を固定長配列 `[52]*MemoryBoardCard` から可変長スライスに変更する。
- 許容範囲は **6〜26 ペア**（12〜52 枚）。26 が従来動作。
- **モバイル縦（幅 < 640px）の初期値を 20 ペア（40 枚）** とする。7 列 × 6 行に収まり、メッセージが 2 行に伸びても耐える余裕がある。それ以外は従来どおり 26 ペア。
- ペア数は**設定 UI から変更可能**にする。モバイルでも 26 ペアを選べる。

初期値を下げるだけでなく設定として露出させるのが要点である。「収まらない」という不具合ではなく「選べる」という仕様になり、苦情の性質が変わる。

## Consequences

### 良い点

- モバイル縦で盤面全体が一望できる。記憶ゲームとして成立する。
- 44×44 のタップターゲットを維持できる（アクセシビリティを犠牲にしない）。
- 横向き推奨バナー（[#1367](https://github.com/yuta-yoshinaga/go_trumpcards/issues/1367) が「UX 逃避策」と呼んだもの）を削除できる。バナー自体が必要な 36px を消費していた。

### 悪い点・受け入れるリスク

- モバイルとデスクトップで既定の難易度が変わる。同一条件での記録比較はできない（本作にスコアランキングは無いため実害は小さい）。
- 盤面が配列からスライスになり、`GetBoard()` / `SetBoard()` のシグネチャが変わる。プレゼンター 2 種とテスト計 65 箇所が影響を受ける。

### この決定を機械的に守らせる仕掛け

ADR だけでは 6 回目が起きうるため、以下を併設する:

- `frontend/e2e/mobile-viewport.spec.ts` に「モバイル既定のペア数で、盤面がプレイエリア内に収まる」アサーションを追加する。
- **可視判定はプレイエリア（スクロール領域）の矩形を基準に行う。** ビューポート基準で数えると、領域に切り取られたカードも「見えている」と誤判定する（実際に本 issue の調査中にこの誤りを踏み、52 枚見えていると誤報告した）。
