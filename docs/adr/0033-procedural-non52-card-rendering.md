# ADR-0033: 非52枚デッキ札の手続き的（CSS/SVG）レンダリング

## Status

Accepted

## Date

2026-07-06

## Context

カードの描画は静的PNGアートに依存している。`public/images/` には標準52枚（`s/c/h/d` の 01–13）＋ジョーカー2枚＋裏面2枚の計58枚しか存在せず、フロントエンド `frontend/src/components/CardImage.tsx` は `card.design`→接頭辞（`s/c/h/d/x`）の閉じた5種マップから `/images/{prefix}{NN}.png` を組み立てて描画する。つまり **「全ての札に対応するPNGが実在すること」** が暗黙の前提になっている。

このため、新規ゲーム候補バッチ（#2880–#2924）のうち **非52枚デッキ**を要するゲーム群がバッチ全体を通してブロックされ続けた:

- タロット（#2911–2914 ほか, 78枚: 21枚のトランプ＋エクスキューズ＋14ランクのスート）
- 花札（#2915–2917 ほか, 48枚）
- カブ札（#2918, 40枚）
- Rook（#2886, 57枚: フレンチスートではない4色 1–14 ＋ Rook 鳥）
- Wizard（#2887, 60枚: 標準52枚＋ウィザード4枚＋ジェスター4枚）

これらの札の専用アートは存在せず、自動生成もできない。

**ドメインモデルはブロッカーではない**。`domain.Card{design,value}` は単なる int であり、`TrumpCards.go` は既に約10種の切り詰め／複数デッキを構築している。ブロッカーは描画レイヤーの少数のチョークポイント（`CardImage.tsx`、`cardAlt.ts`、`cardUtils.ts`、`cli/formatterBase.ts` と、バックエンドの `card_output_helper.go` / `card_design_helper.go` / `web_output_card.go`）に閉じている。

### 検討した代替案

1. **札ごとの専用PNGアートを用意する** — 現行モデルを維持し、タロット約78枚・花札約48枚・カブ札約40枚等の実アートを追加する。最も忠実だが、リポジトリに存在しないアート制作パイプラインを要し、アートが揃うまでゲームはブロックされ続ける。
2. **自己記述子から手続き的（CSS/SVG）に描画する** — 札が任意で描画記述子 `{glyph, label, color, deck}` を持ち、フロントエンドがそれを元にDOM/SVGでカードを描く。アート資産が不要で即時に出荷でき、既存208ゲームのPNG描画は一切変更されない。写実的なアートにはならないが、白地カード＋色付きインクで既存PNG札と調和する。

## Decision

**非52枚デッキの札は、自己記述子に基づき手続き的に描画する（代替案2を採用）。**

札は任意の描画記述子 `{glyph, label, color, deck}` を持てる。

- **記述子が無い**（標準52枚デッキ）⇒ 従来どおり静的PNGパス。既存の全ゲームの出力はバイト単位で不変。
- **記述子が有る**（`deck` が非空）⇒ フロントエンドは手続き描画コンポーネント `CardFace.tsx` に切り替える。

### ワイヤ契約

`WebOutputCard`（`internal/adapter/controller/web_output_card.go`）に `omitempty` の任意4フィールドを追加する:

| フィールド | 用途 |
|-----------|------|
| `glyph` | 中央に描画する記号（例 `"✦"`） |
| `label` | 隅のランク／名称ラベル（例 `"Wizard"`, `"XXI"`） |
| `color` | 色調トークン（例 `"red"`, `"black"`, `"purple"`, `"green"`） |
| `deck`  | デッキ系統ID（例 `"wizard"`）。非空なら手続き描画へ切り替える |

バックエンドの各ゲームは `internal/adapter/presenter/card_output_helper.go` の `faceProvider`（`func(*domain.Card) *CardFace`）を実装し、`cardToOutputWithFace` / `cardsToOutputWithFace` / `playerCardsToOutputWithFace` 経由で自デッキの札に記述子を付与する。標準札には `nil` を返し、既存の `cardToOutput` 系はそのまま使い続ける（オプトイン方式）。

フロントエンドは `Card` 型に任意の `glyph?/label?/color?/deck?` を追加し、`CardImage` が記述子の有無で `<CardFace>`（白地カード＋色付きインク、2:3、角ラベル＋中央グリフ）と従来の `<img>` を振り分ける。CLI／alt テキストも記述子があれば `label`/`glyph` を用いる。

本パスは Wizard（#2887）を最小の実証ゲーム（標準52枚はPNG、ウィザード／ジェスター8枚のみ手続き描画）として検証・出荷する。

## Consequences

**利点**
- タロット／花札／カブ札／Rook／Wizard を含む全ての非52枚デッキがアート制作なしで実装可能になり、長期ブロッカーが解消される。
- 記述子はオプトインであり、既存208ゲームのワイヤ出力・描画は完全に不変（回帰リスクが局所化される）。
- チョークポイント（`CardImage` の分岐1箇所＋描画リーフの数ファイル）に閉じた変更で、ドメイン約200ファイルには波及しない。

**トレードオフ / 留意点**
- 手続き描画の札は写実的なカードアートではなく、記号＋ラベルの様式化された表現になる。忠実な絵柄が必要になった場合は、将来 `deck` 記述子に任意の画像URLを併載してPNGで上書きする拡張余地を残す（現時点では未実装）。
- 各非52枚ゲームは自前の `faceProvider`（glyph/label/color の対応表）と、必要に応じてCUI描画・入力パースを実装する必要がある。本パスは「配管」を提供し、各デッキの「絵柄」は各ゲームが供給する。
- `design` に52枚デッキ外の値（例 Wizard の 5/6）を用いる場合、その意味付けはゲーム内ローカル定数として閉じ、`Card.go` の共有定数（`CardDesignMin/Max` 等）は変更しない。
